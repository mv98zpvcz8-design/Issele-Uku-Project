# Database Design

**Status: implemented (Phase 2).** Every table, enum, generated column,
and RLS policy below exists as version-controlled SQL in
`supabase/migrations/`, plus demo data in `supabase/seed.sql`. No live
Supabase project exists yet — see DEPLOYMENT.md for what's needed to
connect one. This document should stay in sync with the actual migration
files; if they ever diverge, the SQL is the source of truth.

## How this was validated

There's no live Supabase project to test against yet, but every migration
and RLS policy was validated for real against a local PostgreSQL 16
instance (not just read for syntax): a stub of Supabase's `auth` schema,
`auth.uid()`, and the `anon`/`authenticated`/`service_role` roles was
created locally, all migrations were applied in order, and 13 functional
tests were run confirming: anonymous users see only published (and, for
oral history, fully-consented) rows; anonymous writes are rejected;
submissions can be inserted by anonymous users but never read back; the
two-confirmation CHECK constraint on submissions actually rejects an
incomplete submission; a RESEARCHER-role staff account can read
everything (including drafts) but cannot write; an EDITOR can write; and
a non-admin cannot escalate their own role. `supabase/seed.sql` was also
applied and its visibility split checked. See ROADMAP.md for the summary
and DECISIONS.md for anything this uncovered.

## File layout

```
supabase/
  config.toml        Supabase CLI project config (generated by `supabase init`, defaults kept)
  migrations/         One timestamped .sql file per logical table/concern, applied in filename order
  seed.sql            Demo/sample data only — see "Seed data" below
```

## Guiding principles

1. Evidence, confidence, and workflow status are columns, not conventions
   (DECISIONS.md D-005, D-006) — they can be queried, filtered, and
   enforced by RLS, not just displayed by a well-behaved UI.
2. Nothing is publicly visible by default. A row becomes public only when
   its status/consent/permission columns say so, and that's enforced by
   RLS, not by every page component remembering to check.
3. Oral history has an extra, independent consent gate on top of the
   normal content workflow (D-007) — being "published" is necessary but
   not sufficient for an interview to be public.
4. Copyrighted material is metadata-only unless permission is on file
   (D-008) — this is a column the admin UI must respect, not a policy
   enforced by hoping.

```sql

  'DRAFT', 'RESEARCH', 'REVIEW', 'APPROVED', 'PUBLISHED', 'RESTRICTED'

  'DOCUMENTED', 'ORAL_TRADITION', 'INTERPRETATION', 'DISPUTED', 'UNVERIFIED'

create type copyright_status as enum (
  'PUBLIC_DOMAIN', 'PERMISSION_GRANTED', 'COPYRIGHTED_METADATA_ONLY',
  'UNKNOWN', 'RESTRICTED'

  'NOT_REQUESTED', 'REQUESTED', 'GRANTED', 'DECLINED', 'WITHDRAWN'
);
```

### `submissions`
Covers both "corrections" and "material offered for review" (Phase 7).

| column | type |
|---|---|
| id | uuid PK |
| submission_type | text (correction, source_suggestion, copyright_concern, person_identification, new_material) |

Submissions never write directly to public content tables — an admin
reviews a submission and, separately, edits the target record if they
agree (per the brief's correction-workflow rule: "Do not directly modify
published content based on user submissions"). Enforced structurally:
`submissions` has no foreign key or trigger that touches any other
content table.

## Row Level Security (implemented)

Every content table follows the same pattern, built on three
`SECURITY DEFINER` helper functions (defined once in
`20260828120200_profiles_and_auth.sql`, used everywhere else) so policies
never need to subquery `profiles` directly and risk RLS recursion:

- `public.is_staff()` — true for any authenticated user with a `profiles`
  row (i.e. any admin/editor/researcher/reviewer account).
- `public.can_edit()` — true only for `ADMIN`/`EDITOR`.
- `public.can_review()` — true for `ADMIN`/`EDITOR`/`REVIEWER` (used only
  on `submissions`, since triaging the queue is a reviewer's job).

Each content table has a `public_visibility` **generated column**
(`GENERATED ALWAYS AS (...) STORED`) rather than a trigger — e.g. for
`archive_items`:

```sql
public_visibility boolean generated always as (
  verification_status = 'PUBLISHED' and copyright_status <> 'RESTRICTED'
) stored,
```

and the policies just read that column:

```sql
create policy "archive_items: public can read published"
  on archive_items for select using (public_visibility);

create policy "archive_items: staff can read all"
  on archive_items for select using (public.is_staff());

create policy "archive_items: editors can write"
  on archive_items for insert with check (public.can_edit());
-- ...update/delete follow the same using (public.can_edit())
```

`oral_histories`' generated column reflects D-007's extra gate
(`verification_status = 'PUBLISHED' AND consent_status = 'GRANTED' AND
publication_permission = true`), and `submissions` has no public SELECT
policy at all — the public can only INSERT (a write-only mailbox), and a
CHECK constraint (`submissions_confirmations_required`) makes it
impossible for a row to exist without both confirmation booleans true.

RLS cannot redact *part* of a row, so a `restricted_sections`-aware view
(or column-level redaction in the query layer) for partially-restricted
oral history transcripts is deferred to the phase that builds the public
oral-history reader — the schema-level, all-or-nothing gate above is what
Phase 2 delivers.

Profiles get their own small set of policies (self-view, admin-can-view-
all, self-update) plus a trigger (`prevent_role_self_escalation`) that
blocks a non-admin from changing their own `role` column, since RLS is
row-level and can't restrict a single column by itself.

## Seed data

`supabase/seed.sql` is demo data only, applied by `supabase db reset`
against a local/dev database — never automatically against a linked
production project. Every row is prefixed `[SAMPLE]`/`[DEMO]`, uses
obviously fictional names and places, and is deliberately spread across
every evidence type, a DRAFT (unpublished) item, and both an unconsented
and a fully-consented oral history record — so the public-visibility
split can be checked by eye against real running policies, not just
assumed. See CONTENT_GUIDELINES.md rule 5.

## Uncertain and range dates

Rather than forcing every historical date into a single `date` column
(which would falsely imply precision we don't have), date-bearing tables
use three columns: `date_exact` (when a precise date is known),
`date_from`/`date_to` (for a known range or margin of uncertainty), and
`date_display` (the human-readable string actually shown to visitors,
e.g. "c. 1897", "1920s", "before 1950"). The timeline and History listing
(Phase 5) always render `date_display`, but sort chronologically by
`coalesce(date_from, date_exact)` — computed client-side in
`src/lib/timeline/sort.ts` rather than via PostgREST `.order()`, since
`date_from` and `date_exact` are alternative ways of expressing a known
date (an event normally has one or the other) and chaining
`.order('date_from').order('date_exact')` cannot express a coalesce — it
would put any event with only `date_exact` set entirely after every event
with any `date_from`, however much later those actually are. Caught
during the Phase 5 audit; see DECISIONS.md.

### `event_archive_items`
Join table `(event_id, archive_item_id)` — links a historical event to relevant archive records (photographs, documents, recordings), so the timeline and History detail page can show "view record" links. Same RLS pattern as every other join table.

## Export / data portability

Every table above is designed to export cleanly to JSON (via
`supabase db dump` / direct SQL `COPY ... TO STDOUT WITH CSV/JSON`) and to
CSV for the flat, non-array-typed tables. Detailed export commands are
documented in DEPLOYMENT.md once the schema exists.
